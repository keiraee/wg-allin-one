## 一、高优先级（行为与文档承诺不一致，或存在踩坑风险）

### 1.1 真实安装并不会装到 `/opt/wgaio`，README 与 plan3 的承诺未实现

| 来源 | 说法 |
|---|---|
| README「安装会做什么」 | 下载完整套件到 `/opt/wgaio` |
| 设计文档 §3.2 | 安装布局根为 `/opt/wgaio/` |
| plan3 | `if [ "$dry" -eq 0 ]; then dest="/opt/wgaio"` |
| **实际 `lib/install.sh:135-136`** | `dest="$WGAIO_ROOT"`，仅 `--dry-run` 时改 `_stage` |

含义：

- `curl | bash` 时若本地缺套件，`wgaio.sh` bootstrap 会先下到 `WGAIO_DIR`（默认 `/opt/wgaio`）再 `exec`，**此时**安装目录才是 `/opt/wgaio`。README 描述的是这条 happy path。
- 若从 git 克隆或任意完整目录执行 `sudo bash wgaio.sh install`，套件已齐则不会 bootstrap，`dest` 就是当前目录——**装在克隆目录里，不是 `/opt/wgaio`**。
- `/usr/local/bin/wgaio` 会指向那个临时/克隆目录；目录一删，命令即失效。

**不合理点**：安装目标路径依赖「你是怎么把文件弄到机器上的」，而不是产品约定的固定前缀；文档把 bootstrap 行为说成了 install 行为。

### 1.2 `stage_files` 文件清单与 SHA256SUMS / 升级清单不一致

`lib/install.sh` 的 `stage_files` 只复制：

- `lib/core.py`、`lib/*.sh`、`panel/*`、`wgaio.sh`

**不复制**：

- `bin/wgaio`（却在 SHA256SUMS、`tests/test_sh_release.py` 覆盖清单里）
- `SHA256SUMS`（升级的 `check_sha256` / `write_track` 都依赖它）

而 `lib/upgrade.sh` 的 `apply_tree` 会复制 `wgaio.sh`、`SHA256SUMS`、`bin/*`、`lib/*`、`panel/*`。

含义：

- dry-run 产出的 `_stage/` 缺 `bin/` 与 `SHA256SUMS`，和升级后的树不一致；
- 正式安装因 1.1 中 `src==dest` 走「跳过复制」，侥幸靠 bootstrap 解压的完整 tarball 补齐；一旦有人走「完整克隆 + 删掉部分文件再 install」或改过 `dest` 逻辑，就会装出残缺树。

### 1.3 `bin/wgaio` 既不是「装到 /usr/local/bin 的命令本体」，也不能被直接安装

| 来源 | 说法 |
|---|---|
| 设计文档 §3.1 | `bin/wgaio.sh` 是装到 `/usr/local/bin/wgaio` 的命令本体 |
| plan3 | `bin/wgaio` 装到 /usr/local/bin 的薄包装 |
| **实际 `bin/wgaio`** | `exec bash "$(dirname ...)/../wgaio.sh"` |
| **实际 `lib/install.sh:168-171`** | 现写一份 `exec bash '$dest/wgaio.sh'` 到 `/usr/local/bin/wgaio` |

含义：

- 把 `bin/wgaio` 拷到 `/usr/local/bin/` 会去找 `/usr/local/wgaio.sh`（错误）；
- 它只在「套件树内」路径正确（例如 `/opt/wgaio/bin/wgaio` → `/opt/wgaio/wgaio.sh`）；
- 生产入口是 install 现写的包装，`bin/wgaio` 实际是死代码 + 文档误导；设计里的文件名 `bin/wgaio.sh` 也与实物 `bin/wgaio` 不符。

### 1.4 设计文档把「面板公网 HTTPS」列为非目标，产品却已实现并写进 README

| 来源 | 说法 |
|---|---|
| 设计文档 §11 非目标 | 「面板公网 HTTPS 接入（本期仅隧道内 HTTP + 令牌；反代由用户自理）」 |
| 设计文档 §4.2 / 安全面 | 面板仅 VPN 内网 + 令牌 |
| **实现** | 向导可选「公网直接访问」+ 自签 HTTPS（`lib/wizard.sh`），README「公网管理」「安全面」也按公网场景写 |

含义：设计文档已过期，不能再当作范围边界依据；若有人按 §11 拒绝公网/HTTPS 相关改动，会和当前产品行为冲突。

## 二、中优先级（逻辑缺口、边界错误、维护性矛盾）

### 2.1 设计文档多处与实现对不上（清单）

| 设计文档 | 实现 |
|---|---|
| `bin/wgaio.sh` | `bin/wgaio` |
| `lib/backup.sh`（快照/回滚） | 并入 `lib/upgrade.sh` 的 `snapshot` / `cmd_rollback` |
| 升级「对比版本号 + 提交哈希」 | 只比提交哈希与 SHA256SUMS 内容哈希，**不比版本号** |
| main 轨道环境变量 `HY2_REPO_REF` | 实际是 `WGAIO_REF` |
| 第二期 OpenWrt 等 | 尚未有代码，与「本期不做」一致（无矛盾） |

### 2.2 同提交跳过升级 ⇒ 本地损坏无法自愈

`lib/upgrade.sh` 的 `cmd_upgrade`：

1. 提交哈希与 track 相同 → 直接返回「无需升级」；
2. 否则下载后若 SHA256SUMS 内容哈希未变 → 「跳过覆盖」。

设计/README 把这写成特性（避免无意义覆盖），但推论是：

- 本地 `lib/` / `panel/` 被误改、误删后，只要 track 里的提交没变，`wgaio upgrade` **不会修复**；
- 也没有「强制校验并覆盖」子命令。

建议：增加 `wgaio upgrade --verify`（或独立 `wgaio verify`）对本地树跑 `sha256sum -c` 并覆盖修复。

### 2.3 `rollback` 会恢复 `config.json` 与 `.wgaio-track`

`snapshot` 打包了 `config.json` 与 `.wgaio-track`（`lib/upgrade.sh:21`），`cmd_rollback` 整包解开。

风险：

- 升级后用户改过 `config.json`（端口、endpoint、token hash），回滚会**静默撤销**这些修改；
- README 强调「升级只覆盖程序文件，不动 config.json 和 clients/」，用户容易以为回滚也不动配置；
- track 文件一起回滚后，「当前轨道/哈希」显示的是快照时刻，不是回滚发生时刻。

建议：快照排除 `config.json`，或回滚时默认跳过配置并提示。

### 2.4 `read_cfg` 依赖调用方局部变量 `$dest`（动态作用域）

```bash
# lib/install.sh:116-118
read_cfg() {
  ...
  "$py" -c "..." "$dest/config.json"
}
```

`$dest` 是 `cmd_install` 的 `local`。在 bash 里对被调函数可见，故目前在 `init_wg_hub` / `maybe_gen_tls` 链路上能工作；一旦单独调用或重构调用栈，会变成读 `/config.json`。应改为 `read_cfg <path> <key>` 或改读 `"$WGAIO_ROOT/config.json"`。

### 2.5 `panel_bind` 完全未校验

`validate_config` 校验了 `vpn_cidr` / `wg_port` / `endpoint` / `client_dns` / `default_mode` / `lan_cidrs` / `panel_port`，**没有**校验 `panel_bind` 是否为合法 IP 或 `0.0.0.0`。坏值会在 `ThreadingHTTPServer((bind, port))` 时才爆，且是底层异常而非友好错误。

### 2.6 菜单「修改设备」能力窄于 CLI / 面板 / 设计

设计写 `user edit` 可改：名称 / IP / DNS / keepalive / 流量模式。

- CLI（`core.py`）与面板 PATCH 还支持 `--routes` / DNS / keepalive；
- **`lib/menu.sh` 的 `menu_edit_user` 只有改名 / IP / 模式**，没有 DNS、保活、路由段。

双入口能力不对等，和「命令 + 面板共享同一核心、体验对齐」的决策不符。

### 2.7 版本号双处维护，靠字符串 grep 触发 bootstrap

- `wgaio.sh`：`VERSION="0.2.3"`
- `lib/core.sh`：`SUITE_VERSION="0.2.3"`
- bootstrap：`grep -q "SUITE_VERSION=\"$VERSION\""`

只改一处会导致：要么每次启动误触发「版本不一致 → 重新下载」，要么菜单显示版本与真实套件脱节。应单一来源（例如只在 `core.sh` 或只在 `wgaio.sh`）。

### 2.8 `parse_conf` 把对等端「第一行注释」当作设备名

`lib/core.py` 中若 `[Peer]` 后第一行是 `# 临时说明`，会被写成 `name`。`write_conf` 自己写的 `# name: xxx` 能往返；但手工编辑 wg0.conf 时可能误识别，进而影响 `has_client`、改名、`refresh_client_confs`（按名字找私钥备份）。

### 2.9 极小网段（/31 等）自动分配地址会失败

`next_ip`：`range(base + 2, last)`。对 `/31` 可用地址只有两个，区间为空 → 直接「地址已用尽」。`normalize_ip` 对 /31 已放宽网络/广播，但分配器没对齐。正常 /24 场景无影响。

### 2.10 HTTP `HEAD` 会写出完整响应体

`do_HEAD` → `_handle("GET")`，与 GET 同样写 body。不合 HTTP 规范，可能影响某些探测/代理。

### 2.11 会话 cookie 不随滑动续期刷新

服务端 `_authed` 会把 session 过期时间滑到 `now + SESSION_TTL`，但登录时 `Set-Cookie` 的 `Max-Age=SESSION_TTL` 之后不再刷新。结果：连续使用 12 小时后 cookie 过期，会话其实还没过期，用户被踢回登录页。

## 三、低优先级（体验 / 半残状态 / 工程细节）

### 3.1 `uninstall` 后状态半残

- 保留 `lib/ panel/ wgaio.sh`，但删掉 `/usr/local/bin/wgaio` 与 `config.json`；
- 用户无法再用 `wgaio` 命令，只能手动跑保留下来的 `wgaio.sh`；
- `--keep-clients` 留下的 `clients/` 在 wg0（若为 wgaio 管理）已删、配置已删的情况下只是孤儿备份。

与设计「uninstall 彻底清理」的语气不完全一致——实际是「半清理」。

### 3.2 向导 endpoint 校验弱于核心

向导 Python 只用 `^[^:]+:\d+$`；核心 `parse_endpoint` 还限制主机名字符、拒绝 `..` 等。错误在写 config 的 `validate_config` 才爆出，用户面对的是较晚、较长的报错。

### 3.3 公网 + 纯 HTTP 的风险有文档，但向导默认引导能力不对称

向导选公网后默认 HTTPS（推荐项），但用户可选纯 HTTP；README 已警示。逻辑上可接受，建议在向导选 2（纯 HTTP）时再打一句醒目的明文传输警告（目前只有 HTTPS 分支说明「点继续即可」）。

### 3.4 `full_status.default_allowed` 与真实 split 路由不一致

- `default_allowed` = `vpn_cidr + lan_cidrs`
- 真实 `split_allowed` 还会合并**其他设备宣布的网关路由**

状态展示少了一截，面板/CLI 看到的「默认 AllowedIPs」不能代表客户端实际生成结果。

### 3.5 Bootstrap 在「套件齐全但版本字符串不一致」时会用远端盖掉本地

开发机上只改了 `VERSION` 或只改了 `SUITE_VERSION` 时，入口会下载远端套件并 `exec`，**本地未提交修改被忽略**。对调试不友好。

### 3.6 测试与 CI

- `tests/test_sh_release.py` 会校验 SHA256SUMS 覆盖清单与 `sha256sum -c`，能拦住校验和漂移（当前通过）。
- **没有**测试断言「install 落盘包含 bin/wgaio + SHA256SUMS」或「安装根固定为 /opt/wgaio」——1.1/1.2 的缺口正是测试盲区。
- CI 只跑 unittest，未跑 shell 集成（依赖 bash/sha256sum，Windows 本地也常 skip）。

## 四、做得比较扎实的部分（对照后无逻辑矛盾）

1. **写路径**：`wg_lock`（线程锁 + 文件锁）→ `write_conf` 临时文件 rename 原子写 → `wg set` 热更新 → `clients/` 备份；写失败会 `drop_client` 避免私钥与 peer 不一致（`add_peer`）。
2. **服务端拒绝默认路由**：`render_wg0_conf` 不写 `0.0.0.0/0`，PostUp 只做转发 / TCPMSS / 按 VPN 源地址 MASQUERADE，与设计 §7 防坑一致。
3. **网关删除二次确认**：CLI `--force`、API `?force=1`、菜单输入 `force`、面板二次弹窗，语义一致。
4. **令牌**：生成后只打印一次；存 sha256；不进 argv（经 stdin 哈希）；`hmac.compare_digest`；API 只收 `application/json`。
5. **路径穿越**：`client_paths` 先 `normalize_name`；下载 URL 对 path 做 `unquote`。
6. **已有 wg0.conf 不覆盖**、卸载只删带 `wgaio-managed` 的 conf：符合「不动用户原有 WireGuard」的承诺。
7. **`config.example.json` 无真实值**，`.gitignore` 挡 `config.json` / `clients/` / `*.key` / `*.conf`。

## 六、一句话结论

设备管理核心和安全约束是认真做过的；当前最不合理的不是「算法错」，而是 **安装布局（/opt/wgaio）、发版文件清单（bin/SHA256SUMS）、设计文档范围（HTTPS）三条叙事互相打架**，再叠加升级/回滚对配置与本地完整性的处理过于乐观。先对齐「装到哪、装哪些、文档承诺什么」，其余边界问题再按表清即可。
